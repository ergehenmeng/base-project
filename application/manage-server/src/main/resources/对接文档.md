# 第三方接口签名对接规范

本文档适用于服务方明确要求进行签名校验的第三方接口。具体接口地址、业务参数和返回字段以服务方提供的接口说明为准。

## 1. 凭据说明

服务方会为每个调用方提供以下凭据：

| 名称 | 用途 | 传输要求 |
| --- | --- | --- |
| `appId` | 调用方标识 | 放入请求头 `X-App-Id` |
| `appSecret` | HMAC-SHA256 签名密钥 | 仅在调用方本地计算签名时使用，不随请求传输 |

请通过 HTTPS 发送请求，并妥善保管 `appSecret`。密钥泄露后应立即联系服务方重新申请。

## 2. 请求头

每次请求都必须携带以下请求头：

| 请求头 | 必填 | 说明 |
| --- | --- | --- |
| `X-App-Id` | 是 | 服务方分配的 `appId` |
| `X-Timestamp` | 是 | 当前时间的 Unix 毫秒时间戳，例如 `1735689600000` |
| `X-Nonce` | 是 | 随机字符串，最大长度 128 个字符；建议每次请求使用新的值 |
| `X-Sign` | 是 | 按本文档规则生成的签名，小写十六进制字符串 |

四个签名请求头的单个值最大长度均为 128 个字符。服务端校验请求时间与当前时间的绝对差值，超过 60 秒的请求将被拒绝。

## 3. 请求参数规范化

签名使用的 `requestParam` 根据请求类型确定。

### 3.1 JSON 请求

当请求为 `POST` 且 `Content-Type` 以 `application/json` 开头时，`requestParam` 是实际发送的原始 JSON 请求体。

请求体必须保持字节内容一致，以下操作都会导致签名变化：

- 增加或删除空格、换行；
- 调整 JSON 字段顺序；
- 修改数字、字符串或转义形式；
- 先解析 JSON，再重新序列化后发送。

例如，请求体为：

```json
{"query":"a","state":"b","mark":"c"}
```

则 `requestParam` 就是上述完整字符串，不包含代码块标记或额外换行。

### 3.2 GET 和表单参数

GET、`application/x-www-form-urlencoded` 以及其他以请求参数形式提交的请求，按以下规则生成 `requestParam`：

1. 读取请求中的参数名和值；
2. 参数名按 Unicode 字典序升序排列；
3. 同名参数全部保留，并按原请求中的值顺序输出；
4. 使用 `key=value` 形式，以 `&` 连接，不包含 URL 中的 `?`。
5. 空值仍保留等号，例如 `key=`。

例如，原始参数为：

```text
state=b&query=a&mark=c&tag=a&tag=b
state=b&key=1&key=2&tag=b
```

规范化后的 `requestParam` 为：

```text
mark=c&query=a&state=b&tag=a&tag=b
key=1,2&state=b&tag=b
```

## 4. 签名算法

签名过程如下：

```text
data = Base64(requestParam)
stringToSign = appId + timestamp + nonce + data
signature = HMAC-SHA256(appSecret, stringToSign)
```

最终将 `signature` 转换为小写十六进制字符串，并放入 `X-Sign` 请求头。

签名原文不包含 HTTP 方法、请求路径、请求头名称、`?` 或 `appSecret` 本身。

### Java 示例

以下示例仅使用 JDK 标准库，示例中的凭据均为虚拟值：

```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.HexFormat;

public static String sign(String appId, String appSecret, String timestamp, String nonce, String requestParam) throws Exception {
    String data = Base64.getEncoder().encodeToString(requestParam.getBytes(StandardCharsets.UTF_8));
    String stringToSign = appId + timestamp + nonce + data;
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(appSecret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    return HexFormat.of().formatHex(mac.doFinal(stringToSign.getBytes(StandardCharsets.UTF_8)));
}
```

## 6. 错误处理

签名校验失败时，响应体使用统一 JSON 结构，业务结果应以 `code` 为准：

```json
{
  "code": 1031,
  "msg": "签名校验失败"
}
```

常见错误码如下：

| 错误码 | 含义 | 处理建议 |
| --- | --- | --- |
| `1018` | 签名信息为空或格式不正确 | 检查四个签名请求头及时间戳格式 |
| `1023` | 请求时间超出允许窗口 | 使用当前时间重新生成时间戳和签名 |
| `1026` | 签名凭据已过期 | 联系服务方重新申请凭据 |
| `1031` | `appId` 不存在或签名校验失败 | 检查凭据、参数规范化和签名原文 |

## 7. 常见问题

- `X-Sign` 必须使用小写十六进制，不能使用 Base64 或大写十六进制。
- `appSecret` 不应放在 URL、请求头或请求体中。
- JSON 签名必须基于实际发送的原始请求体，不能基于重新序列化后的对象。
- GET/表单签名必须先排序、编码，再生成签名；参数顺序、空格和特殊字符均会影响结果。
- Base64 使用标准 Base64，不使用 URL-safe Base64。
- 服务端当前只校验 nonce 是否存在，不提供 nonce 去重保证；调用方仍应为每次请求生成新的随机 nonce。
